### F2: MODIFIED orbit-conventions spine requirement doesn't extend the baseline `.orbit-runs/ per-change persistence` requirement to cover the two new persistence paths
**File**: openspec/changes/emit-run-summary-jsons-from-workflow-commands/specs/orbit-conventions/spec.md:5
**Description**: The baseline `Requirement: .orbit-runs/ per-change persistence` at `openspec/specs/orbit-conventions/spec.md:135-157` says "The system SHALL define `openspec/changes/<change-name>/.orbit-runs/` as the per-change iteration history directory" — singular, only the changes/<name> path. This change introduces TWO additional persistence locations: (a) `openspec/explore/<name>/.orbit-runs/` for explore named-mode emits (per orbit-run-summary-emit spec.md:5,23) and (b) `openspec/.orbit-runs/` for project-wide audit-drift emits (per spec.md:361). Both are explicitly invoked by the new requirements but neither is documented in the baseline persistence requirement, and the MODIFIED `Internal-run JSON summary format` requirement only modifies the SHAPE, not the LOCATION. A reader of orbit-conventions/spec.md alone would conclude the only valid `.orbit-runs/` location is under `openspec/changes/<name>/`. **Recommendation**: either (1) extend the MODIFIED delta to ALSO modify the `.orbit-runs/ per-change persistence` requirement (broaden it to enumerate the 3 valid root paths with their respective scoping rules), or (2) add a new ADDED requirement to orbit-conventions like `.orbit-runs/ persistence locations` that enumerates all three. The address-reviews schema reference doc already documents the dual whole-repo path (`openspec/.orbit-runs/`) but orbit-conventions's spec doesn't. This is a real cross-doc coherence gap that propagates into archive-time staleness if not closed.

### F3: `/opsx:continue` completeness definition is hand-rolled and may drift from upstream `openspec status --json` `isComplete` semantics
**File**: openspec/changes/emit-run-summary-jsons-from-workflow-commands/specs/orbit-run-summary-emit/spec.md:196-199
**Description**: The `Propose-shaped recommendation logic` requirement defines /opsx:continue's complete state as "proposal.md + design.md + tasks.md + at least one specs/<capability>/spec.md all present" (spec.md:198). But the actual upstream openspec-continue-change SKILL.md (verified via grep) uses `openspec status --json`'s `isComplete: true` field to gate completion. The upstream definition may include more artifacts (e.g., for non-spec-driven schemas) or fewer (e.g., schemas where specs/ are optional). Hand-rolling the artifact check in the emit-layer risks drift from upstream's authoritative definition. **Recommendation**: replace the hand-rolled list with a reference to upstream's `openspec status --json` `isComplete` field, OR add a scenario explicitly testing that the emit-layer's completeness check matches `isComplete: true` from upstream — so future schema additions don't silently break the recommendation logic. Minor — current logic works for the default spec-driven schema, but the spec should be schema-agnostic.

### F4: Apply per-chunk-end emission spec doesn't specify what happens when chunks span MORE than 2 groups, or when the preamble syntax is malformed
**File**: openspec/changes/emit-run-summary-jsons-from-workflow-commands/specs/orbit-run-summary-emit/spec.md:213-241
**Description**: The chunk preamble example shows `Chunk N (groups X)` and `Chunk N (groups X-Y)` covering 1-2 groups (and 2 consecutive groups). The format spec at spec.md:215 reads `Chunk N (groups X[-Y]): <chunk-name>` which only encodes a range, not arbitrary group sets. Two underspecified cases: (a) what if a chunk spans 3+ non-consecutive groups (e.g., `Chunk 4 (groups 6,8,9)`)? (b) what if the preamble has a typo or missing required fields (e.g., `Chunk 2 groups 3-4:` with missing parens)? The current spec falls back to "no-chunking apply" (rule 3) only when the preamble is absent — not when malformed. An implementer might either (i) silently fall back to no-chunking on malformed preamble, or (ii) error out, or (iii) partially parse. **Recommendation**: add a brief "Malformed preamble handling" note: either error and refuse to emit (loud failure surfaces the bug), or fall back to single-emit-at-session-end (graceful degradation). Also note explicitly whether non-range group sets are supported or not. Minor — practical projects use simple ranges, but the spec should be unambiguous.

### F5: Lifecycle per-kind extensions list `sync_specs` but this field maps to a deprecated upstream command (openspec-orbit#6 will remove)
**File**: openspec/changes/emit-run-summary-jsons-from-workflow-commands/specs/orbit-conventions/spec.md:22
**Description**: The orbit-conventions MODIFIED delta lists lifecycle extensions as: `archive_path, audit, sync_specs, unresolved_markers, user_decision`. The `archive-summary-schema.md` confirms `sync_specs` is currently in the archive emit. However, the change's own design.md (line 15) and proposal.md (line 15) reference openspec-orbit#6's removal of `/opsx:sync-specs` (deprecated upstream, absorbed by `openspec archive` in v1.3.1). When #6 ships, `sync_specs` may stop being a meaningful field in the archive emit (or be repurposed). Codifying `sync_specs` in the orbit-conventions universal spine list locks a soon-to-be-stale field into the canonical convention spec. **Recommendation**: either (1) drop `sync_specs` from the orbit-conventions lifecycle extensions list and let the archive SKILL.md document it as a transitional field, or (2) add a note: "sync_specs persists from pre-#6 architecture; will be removed/renamed when #6 lands" so future readers understand the lineage. Trivial impact — but the same forward-look-discipline that D8 / Requirement: No forward-look at other-issue future behavior changes applies in reverse: avoid baking in fields that other open issues will remove.
